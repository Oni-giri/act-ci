## 2. Untested Items & What Would Be Needed to Test Them

1. **Physical Umbrel Hardware Device & `linux/arm64` Runtime Execution:**
   - *Status:* Multi-arch OCI manifests (`linux/amd64` and `linux/arm64`) were built via QEMU/Buildx and verified with `docker buildx imagetools inspect`, and all Level 4 lifecycle checks (including a live nested DinD `act` workflow run) were executed inside containerized `umbrelOS 2.0.2` on `amd64`. However, no physical Umbrel device (such as an Umbrel Home or Raspberry Pi 4/5 running `arm64`) was connected in this session.
   - *What is needed:* SSH + Umbrel login access (or Umbrel 2.0 MCP connection) to a physical `amd64` or `arm64` Umbrel device on LAN/Tailscale to run `rsync` + `sudo umbreld client apps.install.mutate --appId yakitori-act-ci` and complete browser interactive sign-in on hardware.
2. **Interactive Browser Click-Through of Umbrel's `:2000/app-auth` Cookie Handoff:**
   - *Status:* In Level 4 (`umbrelOS 2.0.2`), we verified that unauthenticated requests to `:8755/` and `:8755/tokens` redirect (`302`) to `http://127.0.0.1:2000/app-auth?origin=host&app=yakitori-act-ci&path=...`, while `/api/*` and `/mcp` bypass cookie auth via `PROXY_AUTH_WHITELIST` and enforce Act-CI bearer tokens. Web UI HTML forms, CSRF checks, and live JS polling were tested directly in Levels 1 and 3.
   - *What is needed:* A browser session logged into an onboarded Umbrel UI (`:2000`) to click the app tile on the Umbrel home screen and exercise the cookie-authenticated proxy redirect end to end.
3. **Cloning Private GitHub Repositories via Real GitHub SSH Deploy Key:**
   - *Status:* `GIT_ASKPASS` (HTTPS token) and `GIT_SSH_COMMAND` (SSH deploy key) code paths, `0600` temp file handling outside the workspace, immediate post-fetch wipe, and secret masking are unit-tested, and real HTTPS cloning from GitHub (`https://github.com/Oni-giri/act-ci.git`) ran in Level 4. Cloning an actual private repository over SSH `git@github.com:...` with a live deploy key was not run against GitHub.
   - *What is needed:* A test private GitHub repository and a read-only SSH deploy key pair.

## 3. Decisions, Assumptions & Known Gaps

- **Naming & Repositories:**
  - App source & workflow repository: [`https://github.com/Oni-giri/act-ci`](https://github.com/Oni-giri/act-ci)
  - Published multi-arch image: `ghcr.io/oni-giri/act-ci:0.1.0@sha256:1ea8f527fdcf38d003adf4f22b15e00a312a23bca97cafb2eb2d5cb7125df5f9`
  - Umbrel App Store package branch: [`feat/yakitori-act-ci`](https://github.com/Oni-giri/yakitoris-app-store/tree/feat/yakitori-act-ci) in `Oni-giri/yakitoris-app-store`, scoped strictly to `yakitori-act-ci/`.
- **Sidecar Isolation Without Host Networking:**
  - `onedev` in `getumbrel/umbrel-apps` uses `docker:27.2.0-dind` with `privileged: true` and `network_mode: host`. For Act-CI, we kept `docker:27.2.0-dind` (`privileged: true`, pinned by tag + multi-arch digest) and shared only a dedicated Unix socket directory (`${APP_DATA_DIR}/data/dind-run:/var/run/dind`) between `docker` and `web`, **without** `network_mode: host` and **never** mounting Umbrel's host `/var/run/docker.sock`. Furthermore, Act-CI passes `--container-daemon-socket -` to `nektos/act` (v0.2.98) so workflow job containers do not receive the sidecar's Docker socket either.
- **Core-Layer RBAC & Defense-in-Depth:**
  - Authorization lives in `CiService` (`src/act_ci/service.py`), called identically by `/api/v1/*` and `/mcp`. Even though `tools/list` hides `trigger_run` and `cancel_run` from `viewer` tokens, calling `tools/call` directly with a `viewer` token still hits `CiService._require_role` and is denied (`403` / `-32003`) and logged in `audit_logs`.
  - Admin UI routes live at `/`, `/runs*`, `/repos*`, `/tokens*`, `/activity` (outside `PROXY_AUTH_WHITELIST: "/api/*,/mcp,/mcp/*"`), and an explicit router dependency rejects any request carrying an `Authorization` header (`403`), preventing bearer tokens from ever reaching admin routes even if someone accesses the container directly outside Umbrel.
- **Known v1 Gaps (Aligned with Spec & Roadmap):**
  - Single execution slot (`slot-0`) with FIFO queue; parallel multi-slot / multi-host runners are deferred to roadmap.
  - `act` runs in copy mode (`-C`, no `--bind`) with `--no-cache-server`; cross-run `actions/cache` and `actions/upload-artifact` persistence are out of scope for v1.
  - Because `act` runs in copy mode without bind mounts, workflows that inspect repository files inside job steps should include `- uses: actions/checkout@v4` (just like standard GitHub-hosted workflows), whereas workflows running inline shell commands work with or without checkout.
